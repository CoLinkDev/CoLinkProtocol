# Pairing (pairing.v1)

Pairing establishes trust between two devices that have never communicated before. It uses a short numeric code displayed on both screens for the user to visually confirm, preventing man-in-the-middle attacks.

When both peers advertise P2P protocol version `1.3.0` or later, a valid [pair string v1](pair-string.md) MAY authorize automatic confirmation. When both peers advertise `1.4.0` or later, the [pair string v2](pair-string-v2.md) SHOULD be used instead; v1 remains accepted for compatibility. The original numeric-code flow is used only when no pair string is provided.

## Event Types

| Type | Direction | Description |
|------|-----------|-------------|
| `pairing.v1.request` | Initiator → Receiver | Propose pairing with identity information |
| `pairing.v1.exchange` | Receiver → Initiator | Respond with receiver's identity information |
| `pairing.v1.confirm` | Receiver → Initiator | User confirmed pairing code match |
| `pairing.v1.complete` | Initiator → Receiver | Acknowledge confirmation, both sides store trust |
| `pairing.v1.reject` | Either → Either | User rejected or timeout |

## Message Definitions

**pairing.v1.request:**

```json
{
  "type": "pairing.v1.request",
  "payload": {
    "publicKey": "base64(publicKey)",
    "name": "Alice's Phone",
    "nonce": "random-string-32chars"
  },
  ...
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| publicKey | string | Yes | Sender's public key (Ed25519) |
| name | string | Yes | Sender's device display name |
| nonce | string | Yes | Cryptographically random string, participates in pairing code derivation. The reference implementation uses a UUID v4 without hyphens (32 lowercase hex characters). Implementations MAY use any format as long as it is generated by a cryptographically secure random source and encoded as a valid JSON string. |
| pairString | string | No | One-time pair string. v1 is available only when both peers advertise P2P protocol version `1.3.0` or later; v2 requires `1.4.0` or later. When absent, the numeric-code flow is used. |

**pairing.v1.exchange:**

```json
{
  "type": "pairing.v1.exchange",
  "payload": {
    "publicKey": "base64(publicKey)",
    "name": "Bob's Laptop",
    "nonce": "random-string-32chars"
  },
  ...
}
```

| Field | Type | Description |
|-------|------|-------------|
| publicKey | string | Receiver's public key (Ed25519) |
| name | string | Receiver's device display name |
| nonce | string | Cryptographically random string, participates in pairing code derivation. Same format requirements as `pairing.v1.request` nonce. |

**pairing.v1.confirm:**

```json
{
  "type": "pairing.v1.confirm",
  "payload": {},
  ...
}
```

No additional fields. Indicates that the receiver has accepted the pairing through local authorization: either user confirmation of the numeric code or a valid pair string.

**pairing.v1.complete:**

```json
{
  "type": "pairing.v1.complete",
  "payload": {},
  ...
}
```

No additional fields. Acknowledges that the initiator has also stored the trust record.

**pairing.v1.reject:**

```json
{
  "type": "pairing.v1.reject",
  "payload": {
    "reason": "colink:pairing.user_rejected.v1",
    "message": "User declined the pairing request"
  },
  ...
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| reason | string | Yes | Rejection reason |
| message | string | Yes | Human-readable description for logging/debugging |
| details | object | No | Extensible structured metadata. Receivers MUST ignore unknown keys |

Well-known reasons:

| Reason | Description |
|--------|-------------|
| `colink:pairing.user_rejected.v1` | User declined the pairing request |
| `colink:pairing.timeout.v1` | User did not respond within the allowed time |
| `colink:pairing.code_mismatch.v1` | Pairing code does not match |
| `colink:pairing.pair_string_invalid.v1` | Pair string is malformed, unsupported, or not issued by this receiver |
| `colink:pairing.pair_string_expired.v1` | Pair string has expired |
| `colink:pairing.pair_string_unavailable.v1` | Pair string token is reserved, cancelled, or consumed |
| `colink:pairing.identity_mismatch.v1` | Receiver identity does not match the pair string |
| `colink:pairing.generic.v1` | Generic pairing failure not covered by a specific reason |

## Numeric Pairing Code

Both devices derive a short numeric code for the user to visually compare.

**Derivation:**

```
canonical = "domain=colink-lan-pairing-code\n"
          + "publicKeyA=<lexicographically smaller public key>\n"
          + "publicKeyB=<lexicographically larger public key>\n"
          + "nonceA=<pairing.v1.request nonce>\n"
          + "nonceB=<pairing.v1.exchange nonce>"

digest = SHA-256(UTF-8(canonical))
value  = BigEndian_U64(digest[0..8]) % 1_000_000
code   = zero-padded to 6 decimal digits (e.g. "047291")
```

- Inputs: both public keys (lexicographically sorted) + both nonces encoded as the canonical string above
- Public key sorting ensures both sides compute the same value regardless of role
- Nonces are not sorted: `nonceA` is the `pairing.v1.request` nonce, `nonceB` is the `pairing.v1.exchange` nonce
- Truncation: take the first 8 bytes of the SHA-256 digest, interpret as a big-endian unsigned 64-bit integer, compute modulo 1,000,000, and format as a zero-padded 6-digit decimal string

**Example user experience:**

```
Alice's screen: "Pairing with Bob's Laptop. Confirm the other device shows: 847291"
Bob's screen:   "Alice's Phone wants to pair. Confirm the other device shows: 847291. Accept?"
```

If a man-in-the-middle substitutes public keys, the two sides will compute different codes.

## Numeric-Code Flow

```
Initiator                                      Receiver
  │                                              │
  │─── pairing.v1.request ────────────────────→  │  { publicKey, name, nonce }
  │←── pairing.v1.exchange ────────────────────  │  { publicKey, name, nonce }
  │                                              │
  │  Both compute and display pairing code       │
  │                                              │
  │  ┌─ User accepts on receiver ──────────┐     │
  │  │                                     │     │
  │←── pairing.v1.confirm ─────────────────────  │
  │─── pairing.v1.complete ────────────────────→  │  Initiator stores trust; receiver stores trust
  │                                              │
  │        ═══ Paired ═══                        │
  │                                              │
  │  ┌─ User rejects on either side ───────┐    │
  │  │                                     │    │
  │←→─ pairing.v1.reject ─────────────────────  │  { reason }
  │                                              │
```

## Pair-String Flow

```
Initiator                                      Receiver
  │                                              │
  │── pairing.v1.request ─────────────────────→  │  { publicKey, name, nonce, pairString }
  │                                              │  validates and atomically reserves token
  │←─ pairing.v1.exchange ─────────────────────  │  { publicKey, name, nonce }
  │  validates receiver deviceId and publicKey   │
  │←─ pairing.v1.confirm ──────────────────────  │  automatic local authorization
  │── pairing.v1.complete ─────────────────────→ │  initiator stores trust; receiver stores trust
  │                                              │
  │                 ═══ Paired ═══               │
  │                                              │
```

## Rules

1. The initiator sends `pairing.v1.request` as the first message after hello when no trust record exists for the peer.
2. Pair-string pairing is selected only when the request includes `pairString` and the format is supported by both peers:
   - v1 requires both peers to advertise `1.3.0` or later. v2 requires both peers to advertise `1.4.0` or later. The initiator MUST NOT include a pair string whose format the receiver does not support. The existing `publicKey`, `name`, and `nonce` fields remain required, but neither side displays or uses the derived numeric code for authorization.
   - An initiator that cannot parse the supplied pair-string format MUST NOT initiate pair-string pairing from it. A receiver that receives an unsupported pair-string format, or a pair string whose version requirement is not met after hello, MUST send `pairing.v1.reject` with reason `colink:pairing.pair_string_invalid.v1` and end this pairing attempt.
   - Before sending `pairing.v1.exchange`, the receiver MUST validate and atomically reserve the pair string token as specified in the referenced pair string document ([pair-string.md](pair-string.md) for v1, [pair-string-v2.md](pair-string-v2.md) for v2). On failure, it MUST send `pairing.v1.reject` with the corresponding pair-string reason and end this pairing attempt.
   - On success, the receiver sends `pairing.v1.exchange` followed by the existing empty-payload `pairing.v1.confirm` without local numeric-code confirmation.
   - Before accepting `pairing.v1.confirm`, the initiator MUST verify the receiver identity against the pair string. For both v1 and v2, this means verifying both `deviceId` and `publicKey` as specified in the applicable pair-string document. On a mismatch, the initiator MUST send `pairing.v1.reject` with reason `colink:pairing.identity_mismatch.v1`, MUST NOT store trust, and MUST ignore a queued or subsequent confirm.
3. Numeric-code pairing is selected when pair-string pairing is not selected. The receiver responds with `pairing.v1.exchange`; both sides compute and display the pairing code. The receiver's user accepts or rejects, and the initiator's user verifies the code visually and MAY abort by disconnecting or sending `pairing.v1.reject`.
4. Upon receiving an accepted `pairing.v1.confirm`, the initiator stores the peer's trust record and responds with `pairing.v1.complete`. The receiver records pending trust when sending confirm and stores the initiator trust record only after receiving complete. In pair-string pairing, it then consumes the token.
5. Either side MAY send `pairing.v1.reject` at any point. A receiver with a reserved pair-string token MUST cancel it when the pairing is rejected, fails, times out, or the connection closes before complete.
