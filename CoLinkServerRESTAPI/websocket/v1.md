# Cloud WebSocket

> **Current Cloud WebSocket Protocol Version: 1.1.0**
>
> The Cloud WebSocket protocol uses semantic versioning, independently of the P2P and Business protocols. The version is advertised by the connecting client through `wsVersion`.
> - **Major** bump: breaking changes — clients with a different major version cannot establish a compatible Cloud WebSocket session.
> - **Minor** bump: new backward-compatible messages, fields, or capabilities — the server MUST not send a capability to a client that advertises a lower minor version.
> - **Patch** bump: clarifications or bug fixes with no wire-level impact.
>
> When an implementation adopts Cloud WebSocket behavior from a newer document revision, it MUST update the `wsVersion` it advertises to match the Current Cloud WebSocket Protocol Version declared here.

Real-time communication channel between device and cloud server.

## Constants

| Constant | Value | Description |
|----------|-------|-------------|
| `CLOUD_WEBSOCKET_RECOMMENDED_PING_INTERVAL` | 30 seconds | Recommended interval for client application `ping` messages. |
| `CLOUD_WEBSOCKET_RECOMMENDED_PONG_TIMEOUT` | 60 seconds | Maximum interval the server waits for a WebSocket control `Pong` frame. |

## Connection

```
wss://server/ws/v1?ticket=<ticket>&businessVersion=<semver>&wsVersion=<semver>
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| ticket | string | yes | One-time ticket from `POST /api/v1/ws/ticket` |
| businessVersion | string | yes | Business protocol version (semver) to advertise to peers |
| wsVersion | string | no | WebSocket protocol version (semver) supported by this client. Absent or unparseable values are treated as `1.0.0`. |

Obtain a `ticket` via `POST /api/v1/ws/ticket` (see `ticket.md`). The ticket is single-use and expires after 30 seconds.

## Version Exchange and Compatibility

The server's Cloud WebSocket Protocol Version is the Current Cloud WebSocket Protocol Version declared above. Each client advertises its supported version through the `wsVersion` connection parameter.

- A missing or unparseable `wsVersion` MUST be treated as `1.0.0`, so clients that predate this parameter remain compatible with version `1.x` servers.
- The client and server MUST have the same major version. A client with a different major version cannot establish a compatible Cloud WebSocket session; the server MUST reject the WebSocket upgrade.
- Within major version `1`, the server MAY communicate with an older client, but MUST gate every capability introduced in a later minor version on the target client's advertised `wsVersion`.
- Receivers MUST ignore unrecognized Cloud WebSocket message types and unknown fields in recognized messages. They MUST NOT close the connection solely because of an unknown message type or field.

### Version 1.1.0 Capability

Version `1.1.0` adds `notification.push` and `notification.push-ack`.

- A server MUST send `notification.push` only when the target device advertises Cloud WebSocket Protocol Version `1.1.0` or later within major version `1`.
- For a connected target with `wsVersion` `1.0.x`, absent, or unparseable, the server MUST not send `notification.push` and MUST return `2012 push not supported` to the HTTP caller.

## Message Envelope

All messages use a unified JSON format:

```json
{
  "id": "a1b2c3d4-e5f6-7890-abcd-ef0123456789",
  "type": "message.type",
  "from": "deviceId",
  "to": "deviceId | null",
  "correlationId": null,
  "payload": {},
  "timestamp": 1716451200000
}
```

| Field     | Type        | Description                                 |
|-----------|-------------|---------------------------------------------|
| id        | string      | Message UUID (for dedup, ACK, correlation)  |
| type      | string      | Message type identifier                     |
| from      | string/null | Sender device ID (server fills for inbound) |
| to        | string/null | Target device ID (for relay only, null for system events) |
| correlationId | string/null | Set to the `id` of the originating message when this message is a response or follow-up. Server transparently passes this field through on `relay` and `broadcast`; it does not interpret the value |
| payload   | object      | Message-specific data                       |
| timestamp | number      | Unix timestamp in milliseconds              |

## Lifecycle

1. Client obtains ticket via `POST /api/v1/ws/ticket`
2. Client connects with `ticket`, `businessVersion`, and `wsVersion` in query string
3. Server validates ticket → connection established → device marked online
4. Server broadcasts `device.online` to same-account devices
5. Server sends `device.online` for every other currently online device to the newly connected client (catch-up). These messages are identical in format to real-time broadcasts; the client handles them uniformly.
6. Client sends application `ping` every `CLOUD_WEBSOCKET_RECOMMENDED_PING_INTERVAL` to keep alive; the client MUST respond to WebSocket control `Ping` frames with `Pong`, and the server MUST close the connection and consider the device offline when it has not received a control `Pong` for `CLOUD_WEBSOCKET_RECOMMENDED_PONG_TIMEOUT`.
7. On disconnect → server broadcasts `device.offline`

## Server → Device Messages

### device.online

```json
{
  "id": "b2c3d4e5-f6a7-8901-bcde-f01234567890",
  "type": "device.online",
  "from": "660e8400-...",
  "to": null,
  "payload": {
    "name": "My Phone",
    "type": "android",
    "businessVersion": "1.11.0",
    "wsVersion": "1.1.0"
  },
  "timestamp": 1716451200000
}
```

| Field | Type | Description |
|-------|------|-------------|
| name | string | Device display name |
| type | string | Device platform type |
| businessVersion | string | Business protocol version (semver) reported via WebSocket query parameter |
| wsVersion | string | WebSocket protocol version (semver) reported via WebSocket query parameter. Absent if the device did not supply one; treat as `1.0.0` in that case. |

The server distributes `businessVersion` and `wsVersion` as device presence metadata. It does not interpret business protocol messages and does not enforce business-version compatibility for `relay` or `broadcast`. Before sending business messages, the client is responsible for checking the target device's advertised `businessVersion` and choosing a compatible payload, degrading behavior, or skipping the target. The server uses `wsVersion` for its own Cloud WebSocket capability gates as defined in [Version Exchange and Compatibility](#version-exchange-and-compatibility).

  "type": "device.offline",
  "from": "660e8400-...",
  "to": null,

### broadcast

Message broadcasted from another device:

```json
{
  "id": "b8c9d0e1-f2a3-4567-bcde-567890123456",
  "type": "broadcast",
  "from": "660e8400-...",
  "to": null,
  "payload": {
    "type": "clipboard.v1.sync",
    "payload": { "contentType": "text/plain", "content": "Hello from device A" }
  },
  "timestamp": 1716451200000
}
```

Inner `payload` is a business protocol message, same as `relay`.

### relay (inbound)

Message relayed from another device:

```json
{
  "id": "d4e5f6a7-b8c9-0123-defa-123456789012",
  "type": "relay",
  "from": "660e8400-...",
  "to": "770e8400-...",
  "payload": {
    "type": "clipboard.v1.sync",
    "payload": { "contentType": "text/plain", "content": "Hello" }
  },
  "timestamp": 1716451200000
}
```

Inner `payload` is a business protocol message.

### pong

```json
{ "id": "e5f6a7b8-c9d0-1234-efab-234567890123", "type": "pong", "timestamp": 1716451200000 }
```

### notification.push

Deliver a push notification to this device. Sent by the server in response to an HTTP push request (see `push/send.md`).

```json
{
  "id": "msg-push-aaa",
  "type": "notification.push",
  "from": null,
  "to": "660e8400-e29b-41d4-a716-446655440001",
  "correlationId": null,
  "payload": {
    "title": "Deploy complete",
    "body": "prod v2.3.1 is live",
    "group": "ci",
    "url": "https://github.com/actions/runs/12345"
  },
  "timestamp": 1722038400000
}
```

- `from` is always `null` (server-originated).
- `payload` contains only the fields that were supplied in the HTTP request; absent parameters are omitted entirely.
- The device MUST respond with `notification.push-ack` after processing the notification.
- Only delivered to devices with a compatible Cloud WebSocket Protocol Version `1.1.0` capability; the server rejects the HTTP request before sending if the version requirement is not met.

**Payload fields** (all optional):

| Field | Type | Description |
|-------|------|-------------|
| title | string | Push title |
| subtitle | string | Push subtitle |
| body | string | Push content |
| markdown | string | Markdown push content; when present, `body` is ignored by the receiver |
| level | string | Interruption level: `active` / `timeSensitive` / `passive` / `critical` |
| volume | integer | Alert volume for `critical` level, 0–10 |
| badge | integer | Notification badge number |
| sound | string | Notification sound name |
| icon | string | Custom notification icon URL |
| image | string | Notification image URL |
| group | string | Notification group name |
| url | string | URL to open when the notification is tapped |
| copy | string | Text to copy when the notification is copied |
| autoCopy | boolean | Automatically copy push content on receipt |
| call | boolean | Repeat notification sound for 30 seconds |
| isArchive | boolean | Whether to save the push to history |
| ttl | integer | Retention duration for archived pushes in seconds |
| id | string | Notification identifier for update or deletion |
| delete | boolean | Delete the notification identified by `id` |
| action | string | Set to `"alert"` to show an action popup when the app is opened from the notification |
| ciphertext | string | Encrypted push ciphertext |

## Device → Server Messages

### ping

```json
{ "id": "f6a7b8c9-d0e1-2345-fabc-345678901234", "type": "ping" }
```

### notification.push-ack

Acknowledge receipt of a `notification.push` message from the server.

```json
{
  "id": "msg-ack-bbb",
  "type": "notification.push-ack",
  "correlationId": "msg-push-aaa"
}
```

- `correlationId` MUST be set to the `id` of the corresponding `notification.push` message.
- No `payload`, `from`, or `timestamp` fields are required.
- The server resolves the pending HTTP push request and returns a success response upon receiving this message.
- The server MUST validate the ACK before resolving the request:
  - The `correlationId` MUST match the `id` of a `notification.push` message sent on **this same connection** to **this device**. ACKs referencing a push sent on a different connection or to a different device MUST be silently ignored.
  - The `correlationId` MUST reference a push that is still awaiting ACK (i.e. within the 10-second window). ACKs for already-resolved or timed-out pushes MUST be silently ignored.
  - An unrecognized `correlationId` (one that does not match any pending push) MUST be silently ignored.

### relay (outbound)

Request server to forward a message to another device:

```json
{
  "id": "a7b8c9d0-e1f2-3456-abcd-456789012345",
  "type": "relay",
  "to": "770e8400-...",
  "correlationId": null,
  "payload": {
    "type": "message.v1.text",
    "payload": { "messageId": "88a3c4d5-e6f7-8901-abcd-ef0123456789", "text": "hi" }
  }
}
```

Server fills `from` and delivers. `correlationId` is passed through to the receiver unchanged. If target is offline, message is dropped (no offline queue in MVP).

### broadcast

Request server to broadcast a message to all other devices of the same account:

```json
{
  "id": "b8c9d0e1-f2a3-4567-bcde-567890123456",
  "type": "broadcast",
  "payload": {
    "type": "clipboard.v1.sync",
    "payload": { "contentType": "text/plain", "content": "Broadcast clipboard" }
  }
}
```

**Behavior**:
- Server broadcasts to all online devices of the same user **except** the sender
- Offline devices do not receive the message
